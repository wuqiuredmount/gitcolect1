# 全流程监控流程（monitor pipeline）

> 触发词：用户说「**开启一轮监控**」
> 脚本：`scripts/monitor.mjs`　命令：`npm run monitor`
> 建立：2026-10-08

---

## 一、设计依据：从使命推导工程判据

项目使命（`.agents/MISSION.md`）：**促进人类社会一切信息的开放**。

监控不检查「代码好不好看」，只检查「使命有没有被违反」。翻译成四条工程判据：

| 使命要求 | 工程判据 | 对应检查组 |
|---|---|---|
| 信息不能丢 | 数据完整、无静默缺失 | **B** |
| 信息不能自相矛盾 | dev / 对外 / 磁盘三方一致 | **C** |
| 信息必须可达 | 服务可用、资源可取 | **C** |
| 信息不该被内部流程污染 | 内部数据不泄露到对外版本 | **A** |

外加两条工程卫生：**D 代码健康**、**E 仓库状态**。

---

## 二、五组检查

### A 构建健康

| ID | 检查 | 级别 |
|---|---|---|
| A1 | dev 构建通过 | error |
| A2 | 防泄露两道闸就位（release 剔除插件 + 内部工具关闭） | error |

> ⚠️ **A2 故意不真跑 release 构建**。原因：`vite.config.js` 的 `stripInternalAfterBuild`
> 删的是**硬编码路径** `dist/ai-import`（与 `--outDir` 无关）。真跑一次 = 把正在运行的
> 4173（preview 服务 `dist/`）的内部数据目录删掉 ⇒ **监控动作自身造成故障**。
> 故改为配置静态校验。这是本项目监控的一条重要教训。

### B 数据完整性

| ID | 检查 | 级别 |
|---|---|---|
| B1 | manifest JSON 合法 | error |
| B2 | manifest ↔ 磁盘双向一致 | warn（**可自动修复**） |
| B3 | 批次字段完整（name/lat/lng） | error |
| B4 | 坐标范围合法 | warn |

> B2 排除校验中间产物（`_*` / `*verify*`）：它们按
> `frontend-release-security.md` 属 A 类内部文件，**本就不应登记进 manifest**。

### C 服务一致性（核心：dev 与对外是否一致）

| ID | 检查 | 级别 |
|---|---|---|
| C1 | dev(5173) 可达 | info |
| C2 | preview(4173) 可达 | info |
| C3 | 服务端 manifest 与磁盘一致 | error |
| C4 | 批次文件服务端可达 | error |

> C3 需识别 **SPA fallback**：文件不存在时 preview 返回 `index.html`（HTTP 200 + HTML），
> 不能误报成「JSON 非法」—— 那是「该端口未提供 ai-import」的另一种表现。
>
> **历史教训**：4173 曾因走 release 构建而缺失 AI 面板与 `dist/ai-import`，
> 表现为「两端口数据不一致」。修复方式：4173 改用 `npm run share:internal`。

### D 代码健康

| ID | 检查 | 级别 |
|---|---|---|
| D1 | 临时调试代码残留 | warn |
| D2 | 红线文件改动（自上次提交） | info（仅知情） |
| D3 | 无合并冲突标记 | error |

> D2 **不与历史基线比对**。基线是某一时刻的固定快照，正常开发/提交后必然失配 ⇒ 持续噪音。
> 本项定位是「知情」而非「拦截」，列出哪些红线文件被改过供人工判断。

### E 仓库状态

| ID | 检查 | 级别 |
|---|---|---|
| E1 | 工作区状态概览 | info |
| E2 | webcode 权限开关状态 | info |

## 三、执行流程

    用户说「开启一轮监控」
      ↓
    ① 扫描（npm run monitor）
      ↓
    ② 分级报告（✅ 通过 / ❌ 问题 / ⏭️ 跳过 / 🔧 已修）
      ↓
    ③ 自动修复（npm run monitor -- --fix）—— 仅修有 fix 函数的项
      ↓
    ④ 复验（再跑一次，确认问题消失）
      ↓
    ⑤ 总结（哪些修了、哪些需人工决策、哪些是知情项）

### 命令

    npm run monitor              完整一轮
    npm run monitor -- --fast    跳过构建类检查（快）
    npm run monitor -- --fix     自动修复可修项
    npm run monitor -- --json    机器可读输出

退出码：`0` 全部通过 / `1` 存在问题。

---

## 四、修复策略

| 类型 | 处理 |
|---|---|
| **可自动修复**（有 `fix` 函数） | `--fix` 直接修，如 B2 补登记 manifest |
| **需人工决策** | 报告 + 说明理由，**不擅自动手**（如 D1 删临时代码，需确认前提） |
| **知情项** | 列出但不计为问题（D2 红线改动、E1 工作区状态） |

**原则**：
1. **监控动作本身不能造成故障**（A2 的教训）。
2. **破坏性修复必须有人工前提**，不能因为「监控说要删」就删。
3. **区分「问题」与「知情」**，否则告警疲劳。

---

## 五、与既有监控的分工

| 机制 | 监控对象 | 手段 |
|---|---|---|
| `watch-cline` | **Cline（另一个 AI）** | 快照 / diff，基于磁盘事实 |
| `monitor`（本流程） | **项目自身** | 五组检查 + 自动修复 |
| `integrity` | 红线文件哈希 | 基线比对 |
| `pre-commit-check` | 提交时的红线提醒 | git staged 检查 |

四者互补，不重复：`watch-cline` 管协作，`monitor` 管工程健康。

---

## 六、AI 执行约定

1. 用户说「开启一轮监控」→ 直接跑，**不要先问要不要跑**。
2. 跑完**必须尝试自动修复**，不是只报告。
3. 修复后**必须复验**，用事实说明问题是否消失。
4. 需人工决策的项，**明确列出并说明为什么不能自动修**。
5. 全程完成后**做总结**：修了什么、剩什么、建议下一步。

---

## 七、已知边界

- 无法读取浏览器 IndexedDB ⇒ 数据库内部的重复/缺失**检测不到**，只能通过服务端与磁盘比对间接发现。
- 服务未运行时 C 组跳过，不误报。
- `--fast` 跳过 A 组，适合快速巡检。
